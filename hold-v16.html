hold — ram & mem

  
Memory has two banks. ram is normal working space — always writable. mem is a protectable region: names you place there with in mem can be frozen as a block. This is the real-hardware split: mem is a page the MMU can flip read-only.

  
the verbs

  

    
hold x be 5a cell in ram (the default)

    
hold s in mem be 5a cell in mem — the protectable bank

    
keep / freefreeze / unfreeze the whole mem region. A write to frozen mem ends the run — hardware would fault. ram stays writable throughout.

    
hold p holds 3 · insidecarve a region · nest a child cell in it (same memory, finer name)

    
take 3 from x · give 3 to x · back xsubtract · add · decrement — the target is after from/to, so the line reads as English

    
swap a bexchange two cells in one verb — no temp name; the registers are the temp

    
move a to bcopy a value into a cell — the plain store that give/take were dancing around

    
many v of xmultiply in place — x *= v. The loop-of-adds examples earn their shortcut; in arm it's one mul

    
call m · retjump to a mark and come back — a 16-deep return stack the runtime keeps beside your cells, like the wire table. Overflow refuses; ret on an empty stack ends the run. Kernels can stop copy-pasting their bounds checks

    
wipe rzero a whole region (memset). A frozen region refuses — it faults, same as a write

    
when · loop · markbranch if ≤ 0 · jump · label

    
say · sayallprint a cell · print a whole region

    
hear xread the next number from the input tape into a cell. An empty tape blocks the machine — it pauses mid-run, waiting; type on the tape and press enter to continue. End the tape with . to signal EOF (ctrl-D): reads past it give 0. In the arm view it's say in reverse: a call into the OS, then a store.

    
speak routput a region as characters — same cells as sayall, drawn as glyphs instead of digits

    
fetch x from r at iread the cell at a runtime position — x = r[i], where i is a cell's value, not a fixed offset. This is the dereference hold lacked; in arm it's the register-offset load ldr x0, [base, xi, lsl #3]. With it, a fetch-decode loop becomes expressible.

    
diska third bank, always present: 256 raw cells addressed only by fetch … from disk at i / put … into disk at i — no named cells, because disks have blocks, not variables; a filesystem is the program that imposes names on them. The disk survives reset (and the browser session, storage permitting). A run commits to the disk only when it completes.

    
put v into r at iwrite to a computed position — r[i] = v. Together with fetch, enough to run guests as data: a kernel fetches a guest's next instruction, bounds-checks its target with a when, and either stores or reaps the guest — protection as a comparison, not a hardware trap.

  

  
the front panel

  
The memory view is writable. Tap any cell's value — in a zoomed region, or a single-cell tile — type a number, press enter. Before a run, you're setting the machine's initial memory (disk pokes persist immediately). Mid-run, the poke becomes a step of its own and the rest of the run re-simulates from that moment — same code, new history. Hand pokes bypass keep: a front panel outranks the MMU. The terminal's poke name v (or poke region i v) does the same. Try it on a kernel: step until a guest dies, poke its lives cell back to 1 and the monitor shows it breathing — then notice the scheduler still exits, because its remaining counter is separate state you must poke too, and if you rewind the guest's pcs entry it just gets killed again by the same bounds check. The descriptor table, the bookkeeping, the protection — all of it is just cells, and the front panel proves it. The locks are switches too: tap 🔓/🔒 on a region tile, a zoomed header, or the mem bank to keep or free it by hand — mid-run, the rest of the run re-simulates under the new protection. And the screen is a two-way device: tap a pixel to paint it. The tap is a store into fb, so a program can read back what you drew.

  
the boot chain

  
The 🥾 boot example is firmware: it contains no application logic at all — only the machine and one convention. Boot sector at disk 120: a magic word (7), a guest count, then per guest six words — (code start on disk, code length, arena base, arena limit, window base, window length). Firmware verifies the magic (or says 404: no bootable disk), copies each guest's code from disk into code, fills the descriptor tables from the boot record, then performs the hand-off: keep code — load, write-protect, jump. Everything that runs after that moment came from the disk, including the screen driver: 🥾💾 install boot image writes an OS where the app draws by sending (pixel, color) pairs down the pipe, and a driver guest — ordinary code holding the only device window grant — paints them into fb. Drivers external to the kernel, booted from disk: swap the image and the same firmware boots a different OS.

  
the plugged-in uno 🔌

  
The 🔌 window is a real emulated ATmega328P — the $2 chip in an Arduino Uno — running the actual compiled hold/uno firmware (20.9KB flash, 2KB sram, names hashed, examples in flash, disk in EEPROM). It is the web machine emulating the chip that runs the port of itself. The serial line is live: help, ex 1..6, run — and hear blocks at a real prompt. Because the chip's whole state is 32 registers + 2KB of sram, the trace machinery gives it what no physical AVR has: time travel. Scrub the yellow slider backward, poke sram, and history forks — a JTAG debugger cannot do that. The uno's EEPROM and the hold machine's disk share a format: hold disk → eeprom lets you run 🥾💾 install in the IDE and boot that very image on the emulated chip, and eeprom → hold disk brings its writes back. Honest limits: no interrupts or timers (the firmware polls), approximate cycle timing, and the emulated chip typically runs faster than the real 16MHz part. And one more: the flashed firmware is hold/uno v0.1 — it predates the v16 verbs, so move, many, call, ret and the mul rule answer unknown verb on the chip until the firmware is rebuilt. The kernels don't care: guests are data, so the full-ISA guest ops run anywhere the kernel that interprets them fits.

  
the hold OS manual

  
The 🛡 kernels run guests as data: programs are cells, three per instruction — (op, arg, val). The unified 🖥 hold os kernel implements the full ISA — every op 0–16, including the exokernel grants and the boot window store — and at 171 ram / 54 mem cells it still fits the uno build (176/80); earlier kernels each demonstrate a subset. Note the honest distinction: hold os puts open/read/exec inside the kernel — that's a miniature monolithic Unix. The 🛡✨ exokernel proper example does the opposite: the kernel keeps only scheduling, arena bounds, and disk-extent grants, and the guest's own code walks the directory and reads the file — a library filesystem linked into the app, which is the actual exokernel thesis. Everything below is convention written in hold, not machinery: the monitor reads the kernel's tables, the files app reads the disk format, the screen reads fb.

2 k cread cell k of my opened file into my cell c (both bounds checked)

    
3 a _open the file named at my cells a..a+2; kernel resolves name → extent

    
4 c _hear the tape into my cell c; end of tape exits the caller (EOF = ctrl-D)

    
5 a cexec the file named at my cells a..a+2; new pid delivered into my cell c

    
6 p _jump: set my pc to p

    
7 _ vpipe write v; a full pipe blocks

    
8 c _pipe read into my cell c; an empty pipe blocks

    
9 n _sleep n quanta (the scheduler skips my turns)

    
10 a cwait on the pid held in my cell a; its exit status lands in my cell c; blocks while it lives

    
11 i vdraw: color v at screen cell i — protected MMIO into the kernel's fb

    
the ops below began in the 🛡✨ exokernel proper kernel — just enough compute for a guest to bring its own OS — and the unified 🖥 hold os now implements them too

    
12 a vadd the constant v into my cell a

    
13 a pjump to p if my cell a is exactly 0

    
14 a craw disk read through my extent grant: my cell c = disk[grant + value of my cell a]. A read outside the grant reaps the guest — the secure binding: ownership checked once at grant time, only the bound enforced per access

    
15 a bmy cell a += my cell b

    
the ops below belong to the 🥾 boot microkernel — the kernel that doesn't know what a screen is (🖥 hold os also speaks 7/8, and now routes 16 through the same window grant)

    
7 _ v / 8 c _pipe write / blocking pipe read — the only way guests talk. An empty pipe rewinds your pc: blocking is the kernel declining to advance you

    
16 a bdevice store through the window grant: fb[grant + value of my cell a] = value of my cell b. No grant → reaped. The screen driver is just a guest holding the only grant; the kernel routes stores and enforces the window, nothing more

  

  
Blocking is one line of kernel: it writes your old pc back, so the instruction retries next quantum. Violations are lethal: any failed grant check reaps the guest; the system survives. Disk format: cell 0 = file count; directory entries of 5 cells (3 name chars, start, length) from cell 1; data blocks from cell 21; cells 200+ are the swap partition. The disk survives reset and commits only when a run completes. Kernel tables by convention: lives pcs bases limits cbases (read by the monitor and ps), fstart flen (file descriptors), estat zzz pipe, and fb (read by the screen).

  

    
link a b c · link a left/right bwire cells together — any direction, any count. one wire per cell is a list; two make a tree; wires anywhere make a graph.

    
walk a · walk deep afollow the wires and say each value in order · in-order traversal of a tree

    
cut a · unlink a from bclear a's wires · remove one wire — so you can rewire

  

  
the program is the wiring

  
Because wires are addresses in a small wire table the runtime keeps beside your cells — entries you can cut and re-link, without occupying the cells themselves — a program can be a structure that rewires itself and re-runs. The same cells, wired one way then another, give different answers — without a single value moving. Sorting becomes rewiring, not moving: leave the values still, change the arrows, and each walk reads a more-ordered list. This is the family dataflow and graph-rewriting languages live in — Pure Data, spreadsheets, interaction nets — where the connections are the code.

  
walk it, or energize it — two readings of one structure

  
The same wired cells can be read two ways. walk traces the wires one at a time, sequentially — a finger following the diagram. tick makes the wires conduct: every cell recomputes from its inputs, all at once, on a clock edge — the diagram made true simultaneously, like a live circuit.

  
Give a cell a rule and it becomes live: hold sum be add means sum is always the total of whatever wires into it; hold c be inc is a register that counts up each tick; reg holds and latches its input. Wire them with link, then tick (or tick 5) to energize. mul makes a cell the running product of its inputs. not inverts its input — wire a not and a reg into a loop and the pair blinks on its own: an oscillator from two cells, the seed of every clock circuit. An adder settles in one tick with no clock; a counter needs the clock to remember. This is the difference between dataflow you trace and dataflow that's always on — Verilog's world — in one machine, a verb apart.

  
The clock is a cell too. An inc cell left to run is the tick counter — hold clock be inc and it holds the current tick, visible on the strip. Wire other cells to it and they react to time: alarm be add fed by clock and a constant tracks the clock live. Time isn't a hidden feature; it's memory that counts itself, and everything else is derived from it by wiring — exactly how real hardware builds every clock from one signal.

  
the arm ⇄ toggle

  
Turn on arm ⇄ to see each line compile to ARM64. The strip is a base register (x28 for ram, x27 for mem); a cell is [base, #offset]. Arithmetic is load/op/store. And keep — which used to have no hardware form when it locked single cells — now compiles to a real mprotect on the mem pages, because you freeze a region, not one cell. The split earns its keep: mem is exactly what hardware can protect.
